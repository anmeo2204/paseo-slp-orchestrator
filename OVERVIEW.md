SLP Orchestrator runs a Supervisor–Lead–Peer multi-agent delivery pipeline inside Paseo. You talk only to the Supervisor. It drafts a product spec with you in chat, and after your approval delegates each feature to its own Lead in its own Git worktree. Every feature merges into a shared QA branch, a QA Lead verifies that branch, and the Supervisor merges it into your base branch when the result is accepted.

How it works: every agent receives a private MCP tool bus (`slp-bus`) hosted by the plugin on a loopback port and sees only the tools of its role. A feature Lead defines its pipeline as `[planning]? -> implement`: an optional planning stage with advisor peers that produces a locked brief, then one implement stage with exactly one developer peer. Peers talk only to their Lead; the bus rejects peer-to-peer messages. When the implement stage is approved, the Lead calls `slp_finalize_pipeline` and the engine merges the feature branch into the QA branch with `git merge --no-ff`. After the last feature merges, feature Leads are archived and the QA Lead runs verify stages: QA peers grade every brief criterion in a scorecard and at most one developer fixes. The QA Lead then closes its pipeline and is the only role that calls `slp_report`.

Setup: plugins enabled on the daemon, Paseo 0.11.1 or newer, Linux or macOS, a Node.js 24+ daemon runtime with built-in SQLite, and `git` on the PATH. Run state lives in `~/.slp-orchestrator/orchestrator.sqlite3` (override the directory with `SLP_HOME`), outside your repositories.

Operating modes: `FULL_AUTO` (default, and what the Start run button always sends) has no human gates. `SEMI_AUTO` adds a gate before each pipeline merges; `STEP_BY_STEP_DEBUG` also adds a gate after each stage. Other modes are set through the `slp.run.start` or `slp.run.set_mode` RPC. Per-role model, thinking and permission defaults, the shell watchdog, peer forking (off by default) and the rework cap per stage (default 3) live in Paseo's host-wide plugin settings.

Write boundaries: the Supervisor, the QA Lead, advisor peers and QA peers are read-only. Only the developer peer of a running stage writes, inside its pipeline worktree. Every role is denied `git push` and control of the Paseo daemon or CLI. These are application-level permission-hook rules.

Project workflows: selecting a repository seeds `.slp/SUPERVISOR.md`, `.slp/LEAD.md`, `.slp/QA_LEAD.md` and `.slp/peers/*.md` only when `.slp/` has no role files yet; existing files are never overwritten, and a missing `QA_LEAD.md` is re-seeded. Peer front matter declares `role`, `description`, `kind` (`advisor`, `developer`, `qa`) and the prompt-level convention `tier` (`feature`, `integration`). The `slp-manager` skill (Skills tab → Init skill slp-manager) guides a regular coding agent through generating project-specific roles and `.slp/standards/TEST_POLICY.md`. See [project workflow configuration](docs/project-workflows.md) for the file format, pipeline JSON and snapshot behavior.
